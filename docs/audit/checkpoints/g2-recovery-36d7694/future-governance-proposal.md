# Proposed future governance — INACTIVE, requires explicit approval

This is a new prospective rule proposal, not a reconstruction of lost coordinator rules. It does not reset, legitimize or conceal reported historical mechanical 19/16 or semantic 10/8. Preserve those as unreconciled historical evidence; pending R-050-SUM-MANUAL authorization stays separate and unused. No correction counters are charged by writing this proposal.

## Scope and accounting

Approve an exact signature/GAP/SF packet, source hashes, canonical decision, allowed production/test files and gates before execution. Work on one packet at a time. Revalidation-only packets allow no production change. Routine source-backed catalog implementation requires its own explicit pre-approved clause-to-fact scope; new unrelated facts cannot be added during it.

Track prospective work in a separate, dated ledger with root ID, evidence, category, touched files/assertions, equivalence proof, authorization and actual consumption. Report historical and prospective counters side by side, never as one silently reset total. Count each independent root once; repeated instances of the same demonstrably identical root are one entry. Grouping by provider/file is not proof of common root. Ambiguous independence stops.

## Proposed categories and limits

| Work | Prospective permission after approval | Counting |
| --- | --- | --- |

| Ledger/signature closure | Only individually complete current receipts under the approved packet | Separate from correction counters; no inferred closure or duplicated credit. |

A harness repair must preserve exact source fields/count/dedup/order where contracted, customer choice, document priority, selection/evidence, canonical identity, sums/thresholds, provider/product/channel scope and source trust. Prove why the failing expectation is wrong independently of candidate output. Log the root before repairing; rerun the smallest gate, then the complete affected closure gate. No generic permissive fallback, assertion removal or silent status relabeling.

## Stop and publication rules

Stop the dependent packet at the first changed insurance meaning, customer-choice/priority/selection violation, source/hash/provenance conflict, canonical ambiguity, unreviewed engine defect, unexplained production regression, accounting mismatch or integrity failure. Do not attempt a second semantic fix under a harness label. Stop before a fourth packet root or thirteenth campaign root. Budget increase requires explicit named authorization; failed proposals do not consume permission for other roots. Independent packet continuation is permitted only if explicitly approved in the campaign decision, with isolation evidence; otherwise stop the campaign.

Publish one atomic validated packet per commit, with exact receipt membership and gate hashes. Stage only approved files; push to the established main workflow only after checking remote ancestry. Revalidation documents must clearly distinguish new validation from lost historical closure. Preserve dirty unrelated candidate files. No force-push, deploy, Railway or environment/secret modification. No build exception is assumed without an identified previously approved failure mode and surviving evidence.
