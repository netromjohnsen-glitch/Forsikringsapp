Vi skal gjennomføre den mest omfattende correctness-auditen hittil av
Forsikringsassistentens kildebelagte produktkatalog:

SOURCE → CATALOG COMPLETENESS AUDIT

MODELL:
GPT-6 Ultra / høyeste tilgjengelige reasoning.

Dette er en READ-ONLY AUDIT.

IKKE endre produksjonskode.
IKKE endre katalogdata.
IKKE endre canonical facts.
IKKE endre manifests.
IKKE endre source artifacts.
IKKE endre tester.
IKKE endre dokumentasjon i repo.
IKKE commit.
IKKE push.
IKKE deploy.
IKKE reset/revert/stash.
IKKE endre Railway.
IKKE endre .env.local.
IKKE aktiver tracing.

Målet er først å finne og forstå ALLE sannsynlige source-to-catalog gaps.

Rettelser kommer i en separat oppgave etter human review.

==================================================
1 – WHY THIS AUDIT EXISTS
==================================================

Tidligere audits har bevist mye:

- source provenance fungerer
- comparison semantics er hardenet
- optional ≠ included
- document > catalog
- cross-type isolation
- same-product controls
- side-swap
- product presentation
- runtime correctness.

Men manuell rådgivertesting har avdekket en ny mulig blindspot:

Katalogen kan korrekt vise:

"Ikke dokumentert i kataloggrunnlaget"

selv om relevant informasjon faktisk finnes i originalvilkåret, men aldri ble
canonicalisert/materialisert i katalogen.

Tidligere audits spurte hovedsakelig:

"Presenterer motoren katalogen korrekt?"

Denne auditen skal spørre:

"Representerer katalogen de viktige rådgiverrelevante fakta som faktisk
finnes i originalkildene?"

==================================================

Do NOT compare every product against every other product.

==================================================
7 – SOURCE HIERARCHY
==================================================

Inspect all applicable existing local source artifacts.

Typical hierarchy:

1. full policy terms
2. IPID / product sheet
3. official product page
4. documented add-on terms
5. other already-approved official source artifact.

Do not use new web research in the first pass.

The existing source package is the audit corpus.

9 – SOURCE DATE / VERSION
==================================================

Respect known source version/date metadata.

==================================================
10 – FULL SOURCE READING
==================================================

For every exact product, inspect enough of all applicable source artifacts to
identify advisor-relevant coverage information.

Do not rely only on existing manifest fact mappings.

The point is specifically to discover information that may NOT already be
mapped.

==================================================
11 – NO OCR UNLESS NECESSARY
==================================================

Use normal text extraction.

OCR only if an applicable official source is genuinely image-only and
necessary.

Report OCR usage separately.

==================================================
12 – ADVISOR-RELEVANT FACT DEFINITION
==================================================

A source fact is a candidate for catalog representation when it could
materially help an insurance advisor understand:

- what is covered
- what is not covered
- coverage scope
- important limit
- insurance sum
- deductible
- duration
- age limit
- kilometer limit
- geographical scope
- waiting period
- payout rule
- replacement/new-value rule
- important condition
- important exclusion
- optional availability
- customer-specific choice structure
- product-level distinction
- major service/benefit
- materially different provider mechanism.

==================================================
13 – DO NOT CANONICALIZE EVERYTHING
==================================================

The goal is NOT:

every sentence in the policy terms becomes a catalog fact.

Examples that often do NOT need independent canonical rows:

- ordinary claims-notification procedure
- generic duty to mitigate loss
- general legal boilerplate
- generic fraud provisions
- definitions that do not create product differences
- administrative clauses
- wording with no realistic comparison value.

Classify such material:

NOT_COMPARISON_RELEVANT

rather than a gap.

==================================================
14 – MATERIALITY TEST
==================================================

For every candidate fact ask:

Would a competent insurance advisor reasonably care about this when
comparing this product with another product?

If YES:
candidate advisor-relevant fact.

If NO:
do not force into catalog.

If uncertain:
REVIEW_REQUIRED.

==================================================
20 – MISSING FROM CATALOG
==================================================

Use:

SOURCE_FACT_PRESENT_BUT_MISSING_FROM_CATALOG

only when:

- applicable source clearly documents the fact
- fact is advisor-relevant
- catalog lacks safe equivalent representation
- it is not merely customer-specific
- it is not already represented semantically elsewhere.

==================================================
21 – TOO COARSE
==================================================

Use:

CATALOG_FACT_TOO_COARSE

when catalog representation exists but omits materially useful structured
detail.

Example pattern:

Catalog:
Totalskade = included

Source:
Totalskade = included
+ 3 years
+ 20 000 km
+ >80 % damage threshold
+ new replacement mechanism.

Do NOT automatically classify every omitted source sentence as TOO_COARSE.

Materiality required.

==================================================
22 – SEMANTICALLY MISMAPPED
==================================================

Use:

CATALOG_FACT_SEMANTICALLY_MISMAPPED

when catalog contains information but under wrong semantic meaning.

Examples conceptually:

annual limit represented as per-event limit

exclusion represented as unavailable coverage

optional component represented as included

new-enrollment age represented as termination age.

This is potentially high severity.

==================================================
23 – STRUCTURAL MAPPING GAP
==================================================

Use when:

source concept is represented partially or under a different structure such
that cross-provider comparison becomes misleading/incomplete.

Example:

Provider A:
Feriegaranti
- 14 days
- 2 000/day

Provider B:
Leiebil
- 15 days

Do not assume they are equivalent.

Audit whether there is a shared higher-level concept plus provider-specific
children.

==================================================
24 – PROVIDER-SPECIFIC DETAIL
==================================================

Some source facts are useful but inherently provider-specific.

These should often remain nested detail.

Do NOT force symmetric unknown on every other provider.

==================================================
25 – CUSTOMER-SPECIFIC
==================================================

Facts such as:

actual selected deductible
actual selected insurance sum
actual insured value

may correctly be absent from product catalog.

Catalog may instead document:

selectable range/options
"specified in policy schedule"

where useful.

Do not flag missing actual customer value as catalog gap.

==================================================
26 – OPTIONAL COMPONENT
==================================================

Optional coverage must remain optional.

Audit whether source-backed optional components are:

- represented
- attached to correct products
- correctly scoped
- not materialized as selected.

==================================================
27 – PARENT / CHILD
==================================================

Before declaring missing:

check whether information is already represented through:

parent concept
child facts
provider-specific nested detail.

Do not create duplicate canonical facts.

product.

==================================================
55 – ROOT CAUSE MUST NOT BE ASSUMED
==================================================

A missing visible comparison fact can originate from several layers:

SOURCE
→ source package incomplete

EXTRACTION / SOURCE PARSING
→ source contains fact but audit/parser misses it

CATALOG
→ source fact never entered

CANONICAL MODEL
→ no suitable semantic representation exists

INHERITANCE
→ fact exists but is not inherited to correct product

ADD-ON
→ fact belongs to optional component but is attached incorrectly

APPLICABILITY
→ fact is valid only for specific product/type/version

PRESENTATION
→ catalog contains fact but UI does not expose it.

Trace enough evidence to distinguish these.
