Vi skal gjennomføre en full READ-ONLY:

NITO PRE-PILOT SECURITY, GDPR & PRODUCT READINESS AUDIT

av Forsikringsassistenten.

MODELL:
GPT-5.6 Medium.

Dette er en AUDIT.

IKKE gjør kodeendringer.
IKKE rett bugs.
IKKE endre dokumentasjon.
IKKE endre Railway.
IKKE endre environment variables.
IKKE endre .env.local.
IKKE aktiver production tracing.
IKKE commit.
IKKE push.
IKKE deploy.
IKKE reset.
IKKE revert.
IKKE stash.

Hvis du finner problemer:
DOKUMENTER dem.

Vi skal gjennomgå funnene før rettelser.

==================================================
1 – HOVEDMÅL
==================================================

Vi vurderer om Forsikringsassistenten er klar til en begrenset intern pilot
hos NITO Forsikringssenter med ekte forsikringsrådgivere.

Piloten kan innebære behandling av ekte kundedokumenter.

Audit skal svare på to hovedspørsmål:

A.
Er den tekniske løsningen sikker og personvernmessig forsvarlig nok til at
ekte kundedata kan behandles i en kontrollert pilot?

B.
Er produktet modent nok til at en annen forsikringsrådgiver kan bruke det
uten at utvikleren sitter ved siden av og forklarer/redder arbeidsflyten?

==================================================
2 – VIKTIG BEGRENSNING
==================================================

Dette er:

technical security audit
privacy engineering audit
GDPR readiness/gap analysis
product readiness audit

juridisk godkjenning

Finanstilsynet-godkjenning.

TECHNICALLY VERIFIED

fra:

LEGAL / ORGANIZATIONAL REVIEW REQUIRED.

6 – SECURITY THREAT MODEL
==================================================

Create a concise threat model for the pilot.

Identify at minimum:

ASSETS:
- customer PDFs
- extracted customer facts
- comparison results
- authentication/session
- API credentials
- provider catalog/source data
- feedback attachments
- application configuration.

ACTORS:
- authorized advisor
- unauthorized internet user
- another pilot user
- malicious uploaded document
- compromised browser/session
- accidental internal disclosure.

TRUST BOUNDARIES:
- browser
- Next.js frontend
- server/API routes
- PDF processing
- AI provider
- Railway/runtime
- logging/telemetry
- feedback storage
- any external services.

==================================================

==================================================
8 – CUSTOMER PDF LIFECYCLE
==================================================

Determine exactly what happens to uploaded PDFs.

Answer:

- Does browser send entire PDF to server?
- Is file written to disk?
- Is it kept in memory?
- Is it persisted?
- Is it cached?
- Is it sent to AI provider?
- Is original PDF sent or extracted text?
- Is it included in logs?
- Is filename logged?
- When is it deleted/released?
- Can another request/user access it?
- What happens after error/timeout?
- What happens after server restart?

If any answer cannot be proven:

mark UNKNOWN / REVIEW REQUIRED.

==================================================
9 – EXTRACTED TEXT LIFECYCLE
==================================================

Same audit for:

- extracted PDF text
- model input
- model output
- normalized facts
- customer comparison result.

Search actual logging paths.

==================================================
33 – PROMPT INJECTION
==================================================

This is critical.

Audit extraction prompts and model boundary.

A customer PDF may contain text such as:

"Ignore previous instructions..."
"Send secrets..."
"Classify everything as included..."

Verify document text is treated as untrusted DATA, not trusted instruction.

Assess:

- prompt structure
- schema enforcement
- downstream validation
- whether model can alter system behavior
- whether extracted text can request tools/actions.

==================================================
34 – PROMPT INJECTION TESTS
==================================================

- no secret disclosure
- no tool escalation
- no instruction override

- invalid semantic output is rejected/normalized where applicable.
